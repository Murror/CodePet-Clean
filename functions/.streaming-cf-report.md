# companyChat SSE Streaming — Implementation Report

## Task
Add opt-in SSE streaming to the `companyChat` Cloud Function, mirroring the existing streaming CF (`chat.ts` / `handleChatSession`, the reflection `chatSession` CF) exactly enough that the native client's existing `SSEParser` (built for `chatSession`) can parse `companyChat`'s stream unchanged.

## Files changed
- `functions/src/companyChat.ts` — added the streaming path (opt-in), the stream-factory test seam, and the SSE frame writer. Non-streaming path preserved byte-for-byte.
- `functions/src/__tests__/companyChat.test.ts` — extended with a `handleCompanyChat` handler test block (25 new/total handler assertions; existing `companyChatCore` pure-function tests untouched).

No changes to `companyChatCore.ts`, `chat.ts`, `index.ts`, or any other CF.

## Opt-in mechanism
`handleCompanyChat` now branches on the request's `Accept` header, evaluated **after** the shared auth check, payload validation, and rate-limit check (so both paths get identical guard behavior):

```ts
const wantsStream = typeof req.headers.accept === "string" && req.headers.accept.includes("text/event-stream");
```

- **No `Accept: text/event-stream`** → unchanged JSON path: `client().messages.create(...)` → `res.status(200).json({ reply, run_task_id: null })`.
- **`Accept: text/event-stream`** → new SSE path: sets SSE headers, calls `client().messages.stream(...)` (via an injectable factory), and writes `delta`/`done`/`error` frames.

Auth failure (401) and rate-limit failure (429) happen **before** the branch and **before** any SSE header is set, so a request with the SSE `Accept` header that fails one of those guards gets a plain non-200 JSON response — exactly like `chat.ts`'s convention (guards run before `res.setHeader("Content-Type", "text/event-stream")` / `flushHeaders()`).

## What's preserved on the JSON path (byte-for-byte)
- Same auth check (`verifyAuth`), same `user_message` validation, same `checkAndIncrement` rate-limit call and 429 body shape.
- Same model: `claude-sonnet-5` (`CHAT_MODEL`, unchanged).
- Same system-prompt construction: `buildSystemPrompt` (static, cacheable, `cache_control: {type:"ephemeral"}`) + `buildContextBlock` (volatile, uncached) as two separate system blocks, in the same order — verbatim from `companyChatCore.ts`, untouched.
- Same `buildMessages` history normalization (drop leading assistant turn, coalesce same-role turns, cap to 20).
- Same `client().messages.create(...)` call shape, same response parsing (`response.content` text blocks joined + trimmed), same success/error response shapes (`{reply, run_task_id: null}` / `502 {error:"generation_failed"}`).
- No tool-calling / `run_task_id` logic touched — both paths still return `run_task_id: null` (this slice keeps it that way per spec).

## Streaming path — what it does
1. Runs the **same** auth + rate-limit guards as the JSON path (shared code, executed before branching).
2. Builds the **same** two system blocks (static cacheable + volatile context) and the **same** message history via `companyChatCore`'s existing functions — no prompt or model change.
3. Sets SSE headers (`Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`), `res.status(200)`, then calls `res.flushHeaders()` if present — identical to `chat.ts`.
4. Calls `client().messages.stream({ model: CHAT_MODEL, max_tokens: 1024, system: systemBlocks, messages })` (default factory) or an injected test factory.
5. Emits one `delta` frame per `content_block_delta` text chunk, then a final `done` frame after `stream.finalMessage()` resolves, then `res.end()` in a `finally`.
6. On any thrown error mid-stream, emits an `error` frame (headers are already sent, so the HTTP status stays whatever was set — 200 — matching `chat.ts`'s convention of not attempting a status change after `flushHeaders()`).

## Exact SSE frame format (mirrored from `chat.ts`)
Newline-delimited SSE, one blank line between frames — `res.write(`event: ${event}\ndata: ${JSON.stringify(payload)}\n\n`)`:

- **`delta`** — one per text chunk:
  ```
  event: delta
  data: {"text":"<chunk>"}
  ```
- **`done`** — once, at the end of a successful stream:
  ```
  event: done
  data: {"model":"claude-sonnet-5","cache_hit":true|false}
  ```
  `cache_hit` is `true` iff `usage.cache_read_input_tokens > 0` on the final message (same rule as `chat.ts`).
- **`error`** — on any exception during streaming:
  ```
  event: error
  data: {"error":"upstream_failure","detail":"<String(err)>"}
  ```

This is byte-for-byte the same event-name set and `data:` JSON shape `chat.ts` emits (only the `model` value differs, reflecting each CF's own model — `claude-haiku-4-5-...` for `chatSession`, `claude-sonnet-5` for `companyChat`). The native `SSEParser` built for `chatSession` needs no changes to consume this.

## Test seam (mirrors `chat.ts`'s exactly)
```ts
export function __setStreamFactoryForTests(factory: () => AsyncIterable<StreamEvent>): void
export function __resetStreamFactoryForTests(): void
```
Same `StreamEvent` union (`{type:"text", text}` / `{type:"done", usage?}`), same injection point (a module-level `_streamFactory` that the handler falls back from to `defaultStreamFactory` when unset). The only shape difference from `chat.ts` is the factory's second argument: `systemBlocks` (an array of the two system blocks: static cacheable + volatile context) instead of a single `system: string`, because `companyChat`'s prompt is genuinely two blocks — the contract (client/messages/AsyncIterable<StreamEvent>) is otherwise identical.

## Test additions (`src/__tests__/companyChat.test.ts`)
Added a `describe("handleCompanyChat", ...)` block (new — no handler-level test existed for this CF before this change; only the pure `companyChatCore` functions were tested). It:
- Mocks `../auth` and `../rateLimit` exactly as `chat.test.ts` does.
- Mocks `@anthropic-ai/sdk` at module level (a fake `Anthropic` constructor whose `messages.create` returns a canned response, and whose `messages.stream` throws if a test forgets to inject a stream factory) — needed because, unlike `chatSession`, `companyChat`'s non-streaming path was never given a test seam of its own; mocking the SDK let the JSON path be exercised without a real network call while leaving the production code path untouched.
- **Pre-existing behavior, guarded (405/401/400)** — 3 tests.
- **JSON path (no `Accept` header) — unchanged**: success returns `{reply, run_task_id: null}` and calls `messages.create` exactly once; 429 short-circuits before any Anthropic call; 502 on upstream failure — 3 tests.
- **New: SSE path (`Accept: text/event-stream`)**:
  - Happy path: injected fake async-generator stream factory → asserts accumulated `res.write()` output contains the exact `delta` frames (text accumulated across chunks) and a final `done` frame with `"cache_hit":true` and `"model":"claude-sonnet-5"`; also asserts `messages.create` (JSON path) was never called.
  - Mid-stream failure: factory yields one `delta` then throws → asserts the partial `delta` frame plus an `error` frame, and that the HTTP status stayed `200` (headers already sent) — same as `chat.ts`'s "mid-stream Anthropic error emits an error frame" test.
  - Pre-stream auth failure with the SSE `Accept` header still returns a plain `401` JSON body (`{error:"invalid_token"}`), no `Content-Type: text/event-stream` header set.
  - Pre-stream rate-limit failure with the SSE `Accept` header still returns a plain `429` JSON body, no SSE header set.
  - 4 tests, 6 assertions area.

Total: `companyChat.test.ts` now has 25 tests (was 15 pure-function tests); full suite is 125 tests across 14 files (was ~122 before this change, net +11 including the 3 baseline-guard tests that hadn't existed for this handler either).

## What is NOT verified without deploy
- **No live Anthropic API call was made.** The streaming path's `defaultStreamFactory` (which calls the real `client().messages.stream(...)`) was never exercised against the real Anthropic API — all streaming tests inject `__setStreamFactoryForTests`, and the JSON-path tests mock the SDK's `messages.create`. The actual `@anthropic-ai/sdk` `messages.stream()` async-iterator shape (event types, `finalMessage()` resolution, `usage.cache_read_input_tokens` field) is assumed identical to what `chat.ts`'s already-shipped `defaultStreamFactory` relies on (same SDK version, same code shape) but was not independently re-verified against a live model response for `companyChat`'s two-system-block payload.
- **No Firebase emulator run.** `onRequest` wrapping (`cors: false`, `secrets: ["ANTHROPIC_API_KEY"]` in `index.ts`) was not exercised — only the plain `handleCompanyChat(req, res)` function was called directly with fake req/res objects, same as `chat.test.ts`'s existing pattern. Real Express header-setting order, `flushHeaders()` behavior under a genuine HTTP response, and any proxy/CDN buffering of SSE in front of Cloud Functions are unverified.
- **No native-client round trip.** The claim that the native app's existing `SSEParser` (built for `chatSession`) can parse this stream unchanged is based on the frame format matching `chat.ts` byte-for-byte in code — it was not tested against the actual Swift/native parser.
- **No verification that already-deployed native app versions are unaffected in production** — only that the JSON code path is untouched in source and passes its own mocked-SDK test; no staged rollout or canary was run.
- **Rate limiting / auth mocks are test doubles**, not the real Firebase Admin SDK (`verifyIdToken`) or real Firestore transaction (`checkAndIncrement`) — same limitation `chat.test.ts` already has, not new to this change.
- `firebase deploy` was intentionally **not run** (parked for the user's re-auth, per instructions).
